# GPU PyFR PASS 1 Failure Diagnosis

This note summarizes the failure modes observed in GPU PyFR PASS 1 and defines the minimal requirements for PASS 2.

## PASS 1 outcomes

- PyFR installed successfully on Gilbreth in a user-space virtual environment.
- The CUDA backend ran successfully on an `a100-40gb` Slurm allocation.
- The smoke test completed successfully in job `10696809`.
- The NASA hump case did not produce valid wall-sampling CSVs, benchmark-evaluation CSVs, or a credible hump MAE.

## Mesh variants attempted in PASS 1

### 1. Curved structured hump mesh

- Job: `10696811`
- Mesh path: the earlier structured/curved hump mesh generated before the linear fallback
- Status: failed before useful time advancement
- Failure class: PyFR element/interface ordering
- Key error:
  - `IndexError: list index out of range`
  - raised inside `pyfr.nputil.fuzzysort`
  - called from face-point sorting during interface setup

Interpretation:
- PyFR did not accept the element/interface topology of this hump mesh.
- This is a mesh/import-side failure, not a physics or time-stepping failure.

### 2. Structured triangular hump mesh

- Job: `10696812`
- Status: failed before useful time advancement
- Failure class: same PyFR interface ordering problem
- Key error:
  - `IndexError: list index out of range`
  - again inside face-point sorting/interface setup

Interpretation:
- Converting the structured hump mesh to triangles did not resolve the topology/interface problem.
- The hump domain still reached a PyFR-unfriendly connectivity state before the solver proper.

### 3. Piecewise-linear triangular hump mesh

- Job: `10696817`
- Status: got furthest in PASS 1
- Failure class: sampler plugin failure after solver setup
- Key error:
  - `ValueError: solve: Input operand 1 has a mismatch in its core dimension 0`
  - raised inside `pyfr.plugins.sampler`
  - specifically during point refinement in `_plocs_to_tlocs`

Interpretation:
- This mesh variant is the current best PASS 1 hump baseline because it advanced past import and solver setup.
- The failure was no longer mesh-interface sorting. It moved to plugin-side point localization and refinement.

## Exact PASS 1 plugin dependency problem

The PASS 1 hump configs enabled all of the following sampler plugins at once:

- `wallprobe1`
- `wallprobe2`
- `profiles`
- `field`
- `evaluation`

These are generated by:

- `scripts/pyfr/build_gpu_pyfr_pass1_case.py`

This means the only hump case that reached the solver still died before output because the plugin chain was too ambitious for PASS 1.

## What PASS 2 must remove first

PASS 2 must not begin by asking PyFR to localize hundreds of wall, field, profile, and benchmark points during the first robust hump execution attempt.

The minimum viable next step is:

1. run the hump case with no sampler plugins at all
2. keep only standard solution writing and pseudo-stat output
3. export snapshots externally after the run
4. postprocess outside PyFR
5. reintroduce only a tiny number of points later, and only after the no-sampler hump case completes

## PASS 2 dependency hierarchy

From safest to most fragile:

1. writer plugin only
2. pseudo-stats plus writer
3. a few interior field points
4. sparse wall points
5. full wall/profile/evaluation sampling

PASS 2 should stop climbing that ladder as soon as a stage fails.

## Practical PASS 2 conclusion

The correct PASS 2 fix is not higher order, more points, or more physics complexity.

The correct PASS 2 fix is:

- preserve the piecewise-linear triangular hump mesh as the first robust candidate
- disable all samplers initially
- prove a hump solution can complete and write `.pyfrs`
- export externally
- only then attempt small controlled probe reintroduction
